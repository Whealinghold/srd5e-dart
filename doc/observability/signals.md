# Signal catalogue

Every metric, span and log event srd5e emits. Must match the code (see
[observability rules](../rules/observability.md), §2 and §10). Consumers use
this to build dashboards and alerts; srd5e cannot run alerts itself.

Add a row for each signal in the same change as its code constant. A signal
whose code has not landed keeps its planned row in its owning spec
(`doc/specs/`), not here.

| Name | Type | Unit | Attributes | Emitted by | Purpose | Suggested monitoring |
|---|---|---|---|---|---|---|
| `srd5e.d20_test.resolve` | Span | | `srd5e.d20_test.kind` (`ability_check`, `saving_throw`, `attack_roll`), `srd5e.ability` (`strength`, `dexterity`, `constitution`, `intelligence`, `wisdom`, `charisma`), `srd5e.d20_test.roll_mode` (`normal`, `advantage`, `disadvantage`; absent for a forced failure), `srd5e.outcome` (`success`, `failure`), `srd5e.d20_test.critical_hit` (`true`, `false`; attack rolls only), `srd5e.d20_test.forced_failure_reason` (`chosen_to_fail`, `automatic`; forced failures only), `srd5e.d20_test.roller_failure` (`unavailable`, `invalid_result`; error spans only); error status on failure | `ResolveD20Test` | Trace one D20 Test; the only signal that carries the recorded exception, including a defective adapter's `Error` | Inspect error-status spans when `errors` alerts, or when a span has error status without an `errors` increment. Do not alert on span error rate as well as on `errors`; they overlap for port failures |
| `srd5e.d20_test.resolved` | Counter | `{test}` | same as the span | `ResolveD20Test` | Throughput and outcome mix | Over at least 500 attack rolls in `normal`, `critical_hit=true` outside roughly 2 to 8 percent suggests a biased roller (expected 5 percent; widened ranges are applied by callers). Covers direct host calls only: no other use case calls `ResolveD20Test`, so combat attack rolls are counted under those use cases' own signals. A `forced_failure_reason`=`automatic` share near 100 percent for one ability, sustained, suggests misapplied caller condition wiring rather than gameplay. Alert on a drop to zero throughput against the consumer's baseline |
| `srd5e.d20_test.duration` | Histogram | `s` | `srd5e.d20_test.kind` | `ResolveD20Test` | Latency, including failed calls; dominated by the injected roller | p99 above 5 times the consumer's baseline for a sustained window; expect microseconds with an in-memory roller |
| `srd5e.d20_test.modifiers` | Histogram | `{modifier}` | `srd5e.d20_test.kind` | `ResolveD20Test` | Size of the `RollModifiers` callers pass (minimum 1) | p99 above 20 sustained suggests a caller accumulating modifiers; dashboard otherwise |
| `srd5e.d20_test.natural` | Histogram | `{face}` | `srd5e.d20_test.kind` | `ResolveD20Test` | The d20 face each rolled call used (1 to 20), so an unfair or stuck injected roller is visible on every face, not only on the natural 20 | Over at least 500 rolled calls in `normal`, any face's share outside roughly 2 to 8 percent (expected 5) points at the roller; a share pinned at one face means a stuck roller. Compare with the `critical_hit` monitor on `resolved`, which sees only the 20 face |
| `srd5e.d20_test.errors` | Counter | `{error}` | `srd5e.d20_test.kind`, `error.type` (`dice_roller_exception`), `srd5e.d20_test.roller_failure` (`unavailable`, `invalid_result`) | `ResolveD20Test` | Port failures leaving the use case, counted once, with why the roller failed | Alert on any non-zero rate sustained over 5 minutes. Split the alert by `srd5e.d20_test.roller_failure`: `unavailable` is infrastructure (the dice source is down; page ops), `invalid_result` is the host's adapter answering a different expression (a contract breach; file a bug). The span of the same call holds the exception |
| `srd5e.content.load` | Span | | `srd5e.outcome` (`success`, `failure`); error status when rejected or when the port threw | `LoadContentSet` | One load; error status when rejected | Trace any load with error status |
| `srd5e.content.decode` | Span (child) | | `srd5e.outcome` (`success`, `failure`); error status when rejected or when the port threw | `LoadContentSet` | The decoding step across the port | Duration against document size |
| `srd5e.content.loads` | Counter | `{load}` | `srd5e.outcome` (`success`, `failure`); `error.type` only when a port threw an `Srd5eException` (FR-086) | `LoadContentSet` | Loads attempted and how they ended | Alert on any `failure` for shipped data |
| `srd5e.content.decode_errors` | Counter | `{problem}` | `srd5e.content.problem_kind` (`syntax`, `unsupported_version`, `missing_field`, `unknown_field`, `wrong_type`, `out_of_range`, `invalid_value`, `duplicate`, `unresolved_reference`, `constraint_violation`) | `LoadContentSet` | Problem kinds in rejected documents | Alert when non-zero for shipped data; a rise in `unsupported_version` means a stale consumer document |
| `srd5e.content.entries_loaded` | Counter | `{entry}` | `srd5e.content.kind` (`species`, `background`, `character_class`, `feat`, `equipment`, `spell`, `magic_item`, `monster`, `poison`, `trap`, `contagion`) | `LoadContentSet` | Volume loaded by kind | Compare per-kind counts across releases |
| `srd5e.content.load_duration` | Histogram | `s` | none (FR-080) | `LoadContentSet` | Load time via `Meter.time`, also when the port throws | p95 regression against the previous release |
