## 1. Purpose and scope

Defines the **envelope** in which game content enters the package: the one JSON format version (`schemaVersion`, currently 1), the root object, ids, the decoder that turns a JSON document into a `ContentSet` or a failure listing **every** problem found (path and kind), the cross-entry checks, the revision table through which content specs request additions, the anti-corruption rules, the use case that runs the decoder with its telemetry, and the embedded-library generator.

Ownership (shared-types-and-ownership.md FR-035, FR-046, FR-047, FR-053, FR-064, FR-065): this spec owns the envelope, ids, decoder, failure type, the **content identity types** (`ContentId`, `ContentIdProblem`, `ContentKey`, `ContentKind`, `ContentEntry`, `MissingContent`; FR-142 to FR-148), **every closed vocabulary type and typed id** (section 3, including `DurationUnit`), `SourceCitation`, the building blocks `NamedText`, `FeatCategory`, `Prerequisite`, `ToolProficiency`, the neutral printed-text family `ContentTextBlock` (FR-150 to FR-152), the **whole-set cross-reference validation** (the only place a reference between entries is resolved; no site is exempt, shared-types-and-ownership.md FR-054) and the generator. Bulk content specs reference these and define none. The shape of each kind's entries is owned by that kind's spec and registered in the revision table (section 5). The baseline registers the root arrays `species`, `backgrounds`, `classes`, `feats`, `spells`, `weapons`, `armor`.

Relations (prose only; the header lists the specs that rank lower, shared-types-and-ownership.md FR-056). The identity types are owned here, so this spec needs nothing from the port spec, which depends on it (shared-types-and-ownership.md FR-064). `ContentSetDecoder`, `validateContentSet`, the embedded index (FR-122) and the typed ids flow to the `BundledContentSource` adapter only. Every content data spec depends on this spec and on content-source-port.md, never on another data spec (shared-types-and-ownership.md FR-047). architecture-guardrails.md calls the generator (its FR-078).

**Out of scope:**

- The `ContentSource` port, `ContentLookup`, `ContentCatalogue`, `InMemoryContentSource`, `BundledContentSource` (content-source-port.md); licensing, `NOTICE.md` and data layout (content-licensing-and-notice.md).
- The shape, field rules and case tables of each kind of entry (their specs), and the bundled SRD entries themselves (a separate data change).
- Rules behaviour: nothing here computes Armor Class, save DCs or Proficiency Bonus. Class features, traits, benefits and spell effects are faithful SRD text (Q7).
- Encoding back to JSON; `dart:io` or network loading in the core (shared-types-and-ownership.md FR-030); detecting a duplicate key inside one JSON object (`dart:convert` keeps the last, Q5).
- A schema version per content spec (shared-types-and-ownership.md FR-034).
- Anything from SRD 5.1 or any other book. Nothing that looked like core fifth-edition material was found missing from the PDF; none is included.

## 4. Requirements

A "problem" is one `ContentProblem` in a `ContentDecodeFailed`. Paths are JSON Pointers (RFC 6901) from the root (`~` as `~0`, `/` as `~1`; root is `""`). "Reject" means the decoder returns `ContentDecodeFailed` with the stated problem.

| Id | Requirement | Source | Path |
|---|---|---|---|
| FR-001 | The decoder MUST accept a JSON document as a `String` and return a `ContentDecodeResult`, a sealed type with exactly `ContentDecoded` (carrying a `ContentSet`) and `ContentDecodeFailed` (carrying the problems), exhaustive in a `switch` without a default. | architecture.md §4, §5, §6; shared-types-and-ownership.md FR-017 | happy |
| FR-002 | Text that is not valid JSON (including the empty string and whitespace only) MUST produce `ContentDecodeFailed` with exactly one problem: path `""`, kind `syntax`. | architecture.md §5 | unhappy (invalid input) |
| FR-003 | A root value that is valid JSON but not an object MUST be rejected with exactly one problem: path `""`, kind `wrongType`. | architecture.md §5 | unhappy (invalid input) |
| FR-004 | A missing `schemaVersion` MUST be rejected with exactly one problem: path `/schemaVersion`, kind `missingField`. No other field is examined. | architecture.md §5, §7 | unhappy (missing content) |
| FR-005 | A `schemaVersion` that is not an integer value in the sense of FR-021 (a string, `1.5`, `null`, a boolean) MUST be rejected with exactly one problem: path `/schemaVersion`, kind `wrongType`. `1.0` is the integer 1 on every platform and is accepted. A whole number outside the safe-integer range is `unsupportedVersion`. | architecture.md §5 | unhappy (invalid input) |
| FR-006 | An integer `schemaVersion` not in the supported set (0, 2, -1) MUST be rejected with exactly one problem: path `/schemaVersion`, kind `unsupportedVersion`. No other field is examined. | architecture.md §4, §7 | unhappy (missing content: unsupported version) |

| FR-016 | The problem list MUST be deterministic and ordered: root fields in the order `schemaVersion` then the registered arrays in revision-table order; array elements by ascending index; fields of an object in the order the owning kind spec declares; unknown keys after the known fields of the same object, in ordinal order; then, after every entry-level problem, the duplicate-id problems (FR-031) grouped by `ContentKind` in the declaration order of FR-142 (`species`, `background`, `characterClass`, `feat`, `equipment`, `spell`, `magicItem`, `monster`, `poison`, `trap`, `contagion`; a kind appears only when its row has landed; within `equipment`, `weapons` before `armor`, then further arrays in row order), and inside a group by ascending position of the later entry. | FR-017 | `ContentDecodeFailed` and `LoadContentSetRejected` MUST each reject an empty problem list with `ArgumentError`; their list MUST be unmodifiable (mutation throws `UnsupportedError`) and a defensive copy. | architecture.md §4, §6; errors-and-results.md FR-021, FR-024 | unhappy (immutability) |

## 5. Model

### Documents

A document is a JSON object: `{"schemaVersion": 1, "species": [], "backgrounds": [], "classes": [], "feats": [], "spells": [], "weapons": [], "armor": []}` (arrays optional). Field order within an object is the order problems are reported (FR-016); fields marked `?` are optional; names are lower camel case. Every entry starts with `id`, `name`, `source?` (FR-034); the owning kind spec declares the rest.

### Revision table

The one place where the format grows (shared-types-and-ownership.md FR-034, FR-035). A content spec requests a row; the row names the shape owner. No row carries a version number: before 0.1.0 all revisions land in the single `schemaVersion`; after it a revision that rejects a previously valid document, or reads it differently, raises the version and is **BREAKING**.

### Domain types

- **Published by `content`, owned here:** the types of section 3 and section 6. `ContentProblem` and the sealed `ContentDecodeResult` live in `content/application/` next to the port. Entry value objects are the kind specs' and implement `ContentEntry`. No aggregate, entity or domain event: entries are reference data compared by value. This spec does not use `Die`.
- **Invariants:** each constructor enforces its own spec's rules and throws `ArgumentError` for a programmer-built invalid instance (FR-093). The decoder validates first, collects problems, then constructs; each rule lives once as a constant or predicate (FR-094). Unique ids are enforced per document by the decoder and by `ContentSet`; references and the Origin rule only by `validateContentSet` (FR-035, FR-140). Every problem with untrusted JSON is a `ContentProblem`; no `Srd5eException` is involved in decoding (FR-141).
- **Decoding algorithm (normative for ordering):** (1) parse JSON, else `syntax`; (2) check the root object and `schemaVersion`, stopping on a problem there (FR-004 to FR-006); (3) decode each kind's entries independently, collecting problems; (4) build the lookup set (FR-095); (5) check duplicate ids over it in FR-016 order (FR-031, FR-098); no reference is resolved (FR-035); (6) with no problems, construct the `ContentSet`.

### Versioning and anti-corruption

- After 0.1.0 `schemaVersion` increases whenever a document valid under the previous version would be rejected or read differently (a new kind or required field, a removed or renamed field, a changed enum value set); every increase is **BREAKING** and updates `supportedSchemaVersions`. Before 0.1.0 all revisions land as the one version. The decoder supports only the current version; an unsupported one is a single `unsupportedVersion` problem, not a `ContentLookup` variant (shared-types-and-ownership.md FR-034). A set has no version; the SRD edition of an entry is `source.document`. Strictness (FR-022) is what makes a bump necessary.
- Anti-corruption: only `JsonContentSetDecoder` knows JSON shapes (FR-073); strict, never lenient (FR-021, FR-022, FR-025); no translation of older editions' terms (FR-074); text verbatim, presentation such as a leading `+` or the "Level 1:" prefix is not stored (FR-029); every problem has a findable path (FR-012, FR-014); bundled content is not trusted more than host content (FR-104); fidelity to the PDF stays a review task (FR-090).

## 7. Observability

Domain types and the `JsonContentSetDecoder` adapter are silent by design (observability.md §3, §7): they report through return values and have no retries, fallbacks or I/O timing the use case cannot see. `LoadContentSet` is instrumented (attribute values: shared-types-and-ownership.md FR-041); the six `srd5e.content.*` signals below are owned here. The seven questions:

1. **What can go wrong?** Not JSON; unsupported version; missing, mistyped, out-of-range or unknown fields; duplicate ids; a port throwing an `Error`, an `Srd5eException` or another object. An unresolved cross-file reference is not a decode problem: `validateContentSet` returns it with no signal (FR-131) and `BundledContentSource` throws it as a packaging error.
2. **How would an operator know?** Error status on the load span, `loads` with `failure`, and `decode_errors` by problem kind.
3. **What is needed to diagnose it?** The paths and kinds in the `LoadContentSetRejected` the consumer holds; paths never enter attributes (FR-085).
4. **What is counted or timed?** Loads, problems, entries and load duration; the duration has no outcome attribute (`Meter.time` fixes attributes before the body runs; observability.md §5).
5. **Is existing instrumentation still correct?** None exists yet; `decode_errors` carries `srd5e.content.problem_kind`, never `error.type` (FR-100).
6. **What should a consumer monitor?** Any `failure` load or non-zero `decode_errors` for shipped content; a sudden change in `entries_loaded` per kind; a duration regression. Known gap: a plain `Exception` thrown by a port (FR-086(c)) shows only as span error status and a `load_duration` measurement.
7. **Is anything now noisy?** No log (FR-083); no per-entry or per-problem signal.

| Signal | Type | Attributes | Purpose | Suggested monitoring |
|---|---|---|---|---|
| `srd5e.content.load` | span | `srd5e.outcome` (`success`, `failure`) | One load; error status when rejected | Trace any load with error status |
| `srd5e.content.decode` | span (child) | `srd5e.outcome` | The decoding step across the port | Duration against document size |
| `srd5e.content.loads` | counter, `{load}` | `srd5e.outcome`; `error.type` only when a port threw an `Srd5eException` (FR-086) | Loads attempted and how they ended | Alert on any `failure` for shipped data |
| `srd5e.content.decode_errors` | counter, `{problem}` | `srd5e.content.problem_kind` (FR-100) | Problem kinds in rejected documents | Alert when non-zero for shipped data; a rise in `unsupported_version` means a stale consumer document |
| `srd5e.content.entries_loaded` | counter, `{entry}` | `srd5e.content.kind` (FR-101) | Volume loaded by kind | Compare per-kind counts across releases |
| `srd5e.content.load_duration` | histogram, `s` | none (FR-080) | Load time via `Meter.time`, also when the port throws | p95 regression against the previous release |

Names and keys are constants in the `content` context (observability.md §5); all six feed `doc/observability/signals.md` in the same change as the code.
